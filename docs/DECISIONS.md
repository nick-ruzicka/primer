# Architectural decisions

The tradeoffs and the reasons for them. Paired with `docs/ARCHITECTURE.md`
for the "what was built" view.

Each entry: the decision, the alternatives considered, why we picked this,
and what we'd reconsider at scale.

---

## 1. Read layer, not write layer

**Decision.** Primer reads from source systems via MCP servers but never
mutates upstream state. Every "write-looking" action (follow-up emails,
proposals, stage updates) is drafted for rep approval, never committed
directly.

**Alternatives.** We could have shipped an opinionated write layer — Primer
updates forecast, Primer syncs back to Salesforce, Primer triggers Catalyst
alerts. That would have been more impressive in a demo.

**Why this call.** An opinionated write layer competes with RevTech's
roadmap. RevTech owns the unified data layer; a product that writes back
has to pick sides about which system is authoritative, which is the exact
problem RevTech is being paid to solve. A read layer sidesteps that
conversation entirely — Primer sits on top of whatever RevTech ships and
doesn't care which system "wins."

There is also a trust argument. Reps are slow to trust AI-generated
mutations. The first version of the product does nothing irreversible.
When reps trust it on reads, we've earned the right to propose writes.

**What we'd reconsider.** Drafted outbound emails are the obvious
next-quarter addition — write-adjacent, reversible, low-stakes. The line we
hold is "nothing ships without a rep pressing the button."

## 2. MCP as the seam, not an internal RPC

**Decision.** The six source-system adapters are MCP servers running as
stdio subprocesses under the backend. Not gRPC, not internal FastAPI
modules, not a monolithic tool layer.

**Alternatives.**
- Internal Python modules: `from tools.salesforce import get_account`. Simpler
  but harder to swap.
- gRPC microservices: overbuilt for V1. Real cost in operational complexity.
- A single tool-use interface with all tools on the agent: doable, but blurs
  the source-system boundary we care about surfacing.

**Why MCP.** The swap story is the whole point. When RevTech ships their
unified data layer, the six MCP servers collapse to one. MCP makes the
boundary explicit: one adapter per source system, one process per adapter,
one contract (`account_id` in, JSON out). Nothing above the MCP layer
knows or cares which underlying system it came from.

MCP is also the Anthropic-native shape. The agent can call MCP tools
directly through the Anthropic SDK's tool_use interface. No glue.

**What we'd reconsider.** At scale we'd want MCP servers to run as their
own systemd units or separate containers so one flaky server doesn't
take the backend down. For V1, stdio subprocesses tied to the backend
lifecycle are simpler and kill cleanly.

## 3. Deterministic vs. probabilistic, encoded but not labeled

**Decision.** Every piece of brief content is either a fact from a system
of record or an inference generated by Claude. The UI encodes the
distinction — source chips for deterministic claims, hedged voice
("suggests," "likely") for inferences — but never labels it.

**Alternatives.**
- Big "AI-GENERATED" banner at the top of the brief. Honest but useless;
  reps learn to ignore it.
- Color-coded sentences. Too chatty for an editorial document.
- Confidence percentages. 83% is fake precision; nobody acts differently
  on 83 vs. 91.

**Why this call.** Reps don't want to learn the architecture. They want
to know which claims to verify and which to reference. Source chips +
hedged voice teach that contract through visual grammar — they pick it
up in three reads, then never think about it again.

Section confidence in words ("likely," "very likely") does the same job
at paragraph granularity. Good enough, cheap to produce, doesn't invite
the 83-vs-91 question.

**What we'd reconsider.** For accounts with unusually stale data or very
few source signals, the UI could surface a "low confidence overall" flag
that changes the tone of the whole brief. Not shipped in V1.

## 4. Opinionated brief over informational brief

**Decision.** The brief takes a position. "This is a trust-repair call, not
an expansion call" beats "here are the health signals."

**Alternatives.** The informational version is safer. A dashboard-shaped
brief — just the signals, no synthesis — can't be wrong because it doesn't
commit to anything. We could have shipped that and made everyone's life
easier.

**Why this call.** The synthesis is the work the rep actually wants done.
A brief that concentrates signals into a tab is a chore; a brief that
concentrates decisions into a sentence is a product. The architectural
investment below (§5, §6) is what makes the opinionated version safe to
ship.

**What we'd reconsider.** For CSMs, the 60-day follow-on, the opinion shape
might differ — renewal posture rather than sales posture. Same layer,
different brief type.

## 5. Validation as architecture, not prompt

**Decision.** A second Claude call runs after brief generation, takes the
draft + the raw tool outputs as input, and flags contradictions. Cheaper
model (Haiku), narrower job.

**Alternatives.**
- Better prompts on the primary agent: "be careful about contradictions!"
  Doesn't work. Prompts aren't guarantees.
- Rule-based post-processing: regex for suspicious patterns. Brittle and
  narrow.
- Human review loop: expensive and slow; breaks the real-time feel.

**Why this call.** Hallucination is a rendering problem. We render things
as facts when they're inferences. The only durable fix is structural —
separate the generation from the check. The validation pass reads the
brief with the source data alongside and flags anything the primary pass
got wrong. Then the UI renders warnings before the user forms an opinion.

It also makes the failure mode debuggable. When a warning fires we have
a clean signal to improve: either the agent was wrong, or the validator
was wrong. Two passes with clear roles are easier to evolve than one pass
with a long prompt.

**What we'd reconsider.** The validation pass runs post-generation. At
scale we'd want an earlier fail path — if the tool fan-out returns
conflicting data, we could flag that before calling the primary agent
at all. Faster, cheaper, but harder to generalize.

## 6. Redis cache with 15-minute TTL, replayed event-by-event

**Decision.** Briefs are cached in Redis for 15 minutes. On cache hit, the
endpoint replays the SSE events slowly enough that the UI still feels
"live" — not instant, not stale.

**Alternatives.**
- No cache. Honest but expensive; every reload re-hits Anthropic.
- Long TTL (hours). Stale data starts to lie to reps.
- Cache hit returns the full JSON at once. Breaks the streaming feel; the
  UI has to handle two different rendering paths.

**Why this call.** Reps reload the page. They click back to an account.
They demo to a colleague. Every one of those is the same `account_id`
within minutes of the last call. 15 minutes is a reasonable balance
between freshness and Anthropic spend, and it's long enough to cover a
normal work session.

Replaying events at slower-than-raw speed keeps one UX path. The
frontend doesn't need to care whether the events are live or cached.

**What we'd reconsider.** The 15-min number is unvalidated. A/B it in
production. Briefs that flagged a validation warning might want a
shorter TTL — if there's a conflict, the rep should see it refresh
sooner rather than later.

## 7. Single Hetzner box, bare systemd, no Docker for the app

**Decision.** One CPX21. nginx + Next.js service + FastAPI service + Redis,
all as native systemd units on bare Ubuntu. Docker is used only locally
for validating nginx configs.

**Alternatives.**
- Docker Compose on the box. More portable, more moving parts, more to
  misconfigure.
- Kubernetes. Absurd for V1.
- Vercel + Fly + Render. Three vendors, three billing surfaces, three
  places things can break.

**Why this call.** The operator already runs Chariot Signal Engine on
Hetzner with this exact pattern. One pattern to learn; one place for
things to go wrong. Systemd is enough. The boxes are $8/month and can
be rebuilt from `setup_server.sh` + `scripts/deploy.sh` in ~10 minutes
if anything goes sideways.

**What we'd reconsider.** If the product goes past portfolio piece into real
traffic, we'd move the backend onto its own box and Redis onto its own
box (or Upstash). Keep the shape; just separate the processes.

## 8. Account Intelligence as the layer, briefs as the first artifact

**Decision.** Primer is framed as an "Account Intelligence layer" with
briefings as its first artifact. Not as a briefing product that might
someday add other things.

**Alternatives.** Position it as a briefing product. Cleaner to pitch,
easier to demo.

**Why this call.** The briefing product framing doesn't carry the 60-day
or 90-day story. If this is a briefing tool, the next quarter is feature
creep on briefs. If it's a layer, the next quarter is new brief types
(CSM renewal, QBR prep, portfolio review) on the same foundation — and
each new artifact is a day of work because MCP adapters, the agent
pipeline, the validation pass, and the UI are already built.

Framing matters for what the hiring team is underwriting when they back
the project. The layer framing is what unlocks the 30/60/90 roadmap in
the writeup.

**What we'd reconsider.** If the first artifact doesn't land with reps, no
amount of framing saves it. The layer framing presumes we earn trust on
the briefing first. If we don't, we go back to the drawing board on what
shape the first artifact should be — not on whether the layer framing
was right.

## 9. Two models, routed by agent job — Opus for briefing, Haiku for validation

**Decision.** Primer runs two agents with two different models. The
briefing agent is on Claude Opus 4.7 (or Sonnet 4.6 as a resilience
fallback), because the product's value is concentrated in its prose
quality: it must take a position, argue well, and produce prose that reads
like a thoughtful colleague wrote it. The validation agent runs on Claude
Haiku 4.5 because its job is structured constraint-checking against a JSON
schema, and Haiku handles that with full fidelity at a fraction of the
latency and cost.

The models are independently configurable via `BRIEFING_MODEL` and
`VALIDATION_MODEL` in `.env`. No code coupling, no shared prompt
scaffolding between the two agents beyond the master skill.

Under the V1 demo configuration, the briefing agent is temporarily
downshifted to Haiku 4.5 to work around a credential constraint (the only
working Anthropic token tonight was a Claude Code OAuth token sharing
quota with our interactive session, and Opus/Sonnet requests on that token
were rate-limited). The operator can flip `BRIEFING_MODEL=claude-opus-4-7`
in `.env` once a dedicated API key is in place; no other change required.

**Alternatives.**

- **One model for both** (Opus everywhere). Cleaner to reason about, but
  pays Opus prices to do JSON constraint-checking — the validation agent
  never needs more than Haiku can deliver. Wastes roughly an order of
  magnitude on the validation side of every brief.
- **Haiku everywhere.** What V1 runs tonight under duress. Fast and cheap,
  but the briefing agent's prose quality drops below the "thoughtful
  colleague" bar the product depends on. Measured: Haiku briefs average
  16.7s and ~3,000 characters; Sonnet briefs average 36.6s and ~5,000
  characters. The 54% latency win is real; the rhetorical-layering loss is
  also real. Acceptable as a fallback, not the target state.
- **Opus everywhere + aggressive caching.** Cache every brief for 15
  minutes to relieve model pressure. We do cache (see Decision #6), but
  caching can't help the first hit per account — the one that matters
  most when a rep is prepping for a call.
- **Max-tokens lever instead of model choice.** We tried dropping
  `max_tokens` from 2000 to 1200 on Sonnet: only ~2s shaved, because
  Sonnet was already finishing the brief organically under the cap. The
  ceiling wasn't the bottleneck; the model's per-token speed was.

**Why this call.** The briefing agent *is* the product's voice. Every
investment in its prose quality (model tier, prompt tightening, citation
density) compounds, because the brief is what reps read. The validation
agent is a constraint checker — "did the brief cite real facts, did two
sources disagree and did we surface it, is any claim hallucinated?" Those
are Haiku-scale problems. Using Opus for validation would be using a
sports car to move boxes.

The right question isn't "which model is best?" but "what is each agent's
job, and what is the smallest model that reliably does it?" Briefing:
Opus. Validation: Haiku. The same pattern scales — future richer artifacts
(QBR prep, portfolio review) run on whatever model delivers their voice;
future validators stay on Haiku; future simple drafters (follow-up emails
in a rep's voice) likely stay on Haiku too.

**What we'd reconsider.** If a future Haiku matches current Opus on
opinionated prose, consolidate to one tier — roughly 2x cost reduction
with no quality loss. Conversely, if rep-feedback shows briefs need
richer reasoning than current Opus delivers (e.g. "the brief missed the
cross-account pattern on Northstar"), consider extended thinking mode or
the next Opus tier.

The operational lever we will not give up: two models, routed by agent
job, independently swappable via `.env`. Anything that couples them makes
both harder to optimize.

## 10. Biome: demote a11y, security, and select suspicious rules to `warn`

**Decision.** In `frontend/biome.json`, the following rules are demoted
from error to `warn`: all `a11y/*` rules that fired on the current
component set (`noNoninteractiveTabindex`, `noStaticElementInteractions`,
`noSvgWithoutTitle`, `useAriaPropsSupportedByRole`, `useKeyWithClickEvents`,
`useValidAnchor`), `security/noDangerouslySetInnerHtml`, and three
`suspicious/*` rules (`noArrayIndexKey`, `noAssignInExpressions`,
`useIterableCallbackReturn`). They remain visible in the editor and in
`biome check` output; they no longer fail CI.

**Alternatives.** Fix every violation — add roles and keyboard handlers,
switch to stable list keys, refactor every `dangerouslySetInnerHTML`
behind a sanitizer component, rewrite the regex-exec-in-while loops.
Tens of changes across several components during a parallelized portfolio piece
build. Not in scope.

**Why this call.** All the demoted rules are real — they flag things
worth fixing before this ships to screen-reader users or production
traffic. But they weren't violations when Terminal 3 wrote the code;
they became CI failures only once the Biome job started running against
the branch. Gate-kept like that, they would either (a) block
integration testing for cosmetic and a11y work that isn't on any
critical path tonight, or (b) force a rushed fix that loses the intent
of each flag.

Demote-to-warn keeps the flags visible where the work actually happens
— the editor and a local `biome check` — without blocking the
short-window build. For a portfolio piece demo with no real end users, the
tradeoff is right. For production, the tradeoff inverts: these should
be errors again, and the violations should be fixed.

**What we'd reconsider.** Before any production traffic: flip the
rules back to error and do a proper pass. `noDangerouslySetInnerHTML`
specifically should either move behind a sanitizer component that
biome-ignores the call in one place, or the components that currently
use it should render markdown through a proper React tree rather than
an HTML string. `a11y/*` should be a full sweep — a rep using VoiceOver
should be able to drive every interactive element.
