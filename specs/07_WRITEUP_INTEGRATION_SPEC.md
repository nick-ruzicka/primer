# 07 — Writeup Integration Spec

The writeup lives inside the product as Mode 4. One URL = prototype + thinking. Hiring manager clicks the link, sees the brief, clicks "Writeup" in the mode switcher, reads the reasoning.

## Location

`frontend/writeup.html` — a separate HTML fragment loaded into the main area when Mode 4 is active. Or inline in `briefing.html` as a hidden div that shows when mode=4.

Recommend inline. One file, no fetch, renders instantly.

## Mode switcher change

Update the segmented control from three items to four:
- Reading (1)
- Prep (2)
- Split (3)
- Writeup (4)

The Writeup button can be visually set apart slightly — smaller font, or a quiet "About this build" label instead of "Writeup." This keeps it from dominating a mode switcher that's otherwise about the product itself.

## Writeup content structure

Presentation-first layout. Each section reads as a scannable slide with:
- A large section header that is the claim, not the topic
- A 1-sentence thesis in slightly larger body type
- 3-5 short bullet points of supporting evidence
- An inline visual moment where relevant (small diagram, pull quote, comparison table)

Collapsible "Speaker notes" expand under each section containing the dense prose version (from our V1 draft). Default: collapsed.

## Section structure

### Hero

```
# Primer
## A pre-call briefing for enterprise AEs

by Nick Ruzicka · April 2026 · takes-home submission

[Open the prototype →]  [Read the architecture ↓]
```

### Section 1 — "We built a read layer, not a write layer"

Thesis: The core architectural move is that Primer never mutates upstream data. It wraps existing APIs, reasons across them, and outputs opinion — but never writes back.

- Six MCP servers, one per source system
- Drafts for rep approval, never direct mutations
- When RevTech ships their unified data layer, MCP servers repoint — Primer doesn't change
- Doesn't compete with RevTech's roadmap, sits on top of whatever they deliver

Visual: simple diagram showing MCP servers as the boundary between Primer and the existing stack

### Section 2 — "The brief takes a position"

Thesis: Dashboards concentrate manual work in one tab instead of five. A briefing that takes a position does the synthesis for the rep — which changes what "prep" means.

- Example: for Northstar Beauty, the brief says "this is a trust-repair call, not an expansion call"
- Rep walks in knowing the posture, not juggling signals
- Comes with real risk — an opinionated product can be wrong
- Architecture (below) is how we make opinion safe to ship

Visual: side-by-side — "what most tools give you" (a tile grid) vs. "what Primer gives you" (a paragraph)

### Section 3 — "Deterministic vs. probabilistic is load-bearing but invisible"

Thesis: Every piece of content is either a fact from a system of record or an inference generated by the agent. The distinction is encoded in the UI but never labeled.

- Deterministic facts carry inline source chips (·N)
- Inferences use hedged voice ("this suggests," "likely")
- Section confidence in words, not percentages ("— likely," "— very likely")
- The rep never learns the architecture; they learn which claims to verify vs. reference

Visual: the same sentence, one with a source chip, one in hedged voice

### Section 4 — "Hallucination guardrails are architectural, not prompted"

Thesis: The failure mode that kills trust in tools like this is confident wrong answers. We prevent them at the rendering layer, not the prompt.

- Structured output with per-field source attribution
- Validation agent reads the brief against raw data, flags contradictions before render
- Refusal rather than inference when sources are missing
- Staleness timestamps on every cached fact

Visual: screenshot of a validation warning in the brief ("Forecast vs. evidence conflict")

### Section 5 — "What I intentionally left out"

Thesis: A V1 is defined more by what it excludes than what it includes.

- No chat — reps don't want to ask questions, they want a prepared read
- No generic dashboards — only flagged and contradictory data gets prominence
- No write-back — drafted proposals for rep approval, never direct writes
- No multi-account briefings — scoped to one rep, one call
- No custom confidence weighting — a validated scoring model matters more than a configurable one

Visual: none needed, this is a text section

### Section 6 — "Production architecture"

Thesis: Account Intelligence is the layer. The briefing is one artifact. Future artifacts live on the same foundation.

- 30 days — what's here, piloted to one AE team, full logging
- 60 days — CSMs (different brief type, same layer), drafted follow-up emails, rep voice profiles
- 90 days — portfolio briefings, renewal risk alerts, QBR prep as a separate brief type
- When RevTech ships the unified layer — MCP servers repoint, nothing else changes

Visual: timeline graphic with three milestones

### Section 7 — "How I used AI in the build"

Thesis: The prototype went from zero to live in about {X} hours using Claude Code and Claude Design. That itself is a point about what GTM Engineering means in 2026.

- Claude Code for backend, MCP servers, data layer
- Claude Design for the UI system
- Parallel Claude Code terminals for frontend + backend + infra + dataset simultaneously
- This isn't a tool flex; it's the economics argument — teams that invest in building ship differentiation, teams that rent off-the-shelf ship the same thing as their competitors

Visual: screenshot of four Ghostty terminal windows running in parallel

### Section 8 — "Tradeoffs"

Thesis: Every interesting decision was a tradeoff, not a best practice.

- Freshness vs. cost — cached with staleness timestamps
- Source of truth vs. velocity — surface contradictions, don't reconcile
- Opinion vs. informational — opinion is higher leverage but higher risk
- Read-only vs. write-back — read-only earns trust first
- Single-account vs. portfolio — single is enough for V1

Visual: none — text with clear headers

## Visual style

Match the Primer aesthetic:
- Same Fraunces/Inter Tight type pairing
- Same color system (warm dark or light-with-gradient)
- Each section on its own "slide" with generous whitespace
- Reads as an editorial document, not a slide deck PDF

Scrollable, not paginated. The hiring manager scrolls through like a Medium post, not clicks through like a slideshow.

## Implementation

In `briefing.html`, add a hidden container:

```html
<div id="writeup-container" style="display:none">
  <!-- full writeup content here -->
</div>
```

Mode switcher state 4 hides `#main-content` and shows `#writeup-container`. Nothing else needs to change.
